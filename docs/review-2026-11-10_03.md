## 2. 本轮发现

### F-04 低（测试隔离）：失败路径守卫只处理已记录 PID，可能遗留同组 `sleep`、等待 release 的 Hook 和未收尾的采样任务

**位置**

- [`plugin_services.rs:180-198`](../crates/saya-core/tests/plugin_services.rs#L180-L198)：`cleanup_processes` 对记录 PID 单独发送 `SIGKILL`。
- [`plugin_services.rs:232-239`](../crates/saya-core/tests/plugin_services.rs#L232-L239)：只有运行中的采样任务负责写 Hook release 文件。
- [`plugin_services.rs:265-287`](../crates/saya-core/tests/plugin_services.rs#L265-L287)：Drop 中止任务但不 await，随后只按已记录／待映射 PID 清理。
- [`plugin_services.rs:725-752`](../crates/saya-core/tests/plugin_services.rs#L725-L752)：守卫测试只等待父 shell 退出，没有断言其子进程或进程组消失。
- [`plugin_services.rs:70-76`](../crates/saya-core/tests/plugin_services.rs#L70-L76)：Hook 父进程持续等待 release；其后代 shell 持续派生 `sleep`。

**问题一：杀父 shell 不等于回收当前同组子进程**

fixture 的循环是 `while :; do sleep 1; done`。当父 shell 正在等待外部 `sleep` 时，`kill(parent_pid, SIGKILL)` 只终止父 shell，并不自动终止这个子进程。该 `sleep` 最迟约一秒后自然退出，因此不是新的永久无限循环，但在失败路径仍违反“所有已创建测试进程均由守卫回收”的目标。

现有守卫单测也启动同样的 shell，却只通过独立线程等待父 shell，然后检查父 PID 的身份消失。即使同组 `sleep` 当时仍存活，测试仍会通过。生产实现的 `ManagedProcess` 使用进程组信号并确认组清理；新测试守卫没有复用同等语义。

**问题二：Drop 没有释放仍在等待的 Hook**

Hook release 只由采样任务写入。如果运行在等待 release 时失败、panic 或提前展开，Drop 会设置 stopping 并 `abort()` 采样任务，但既不保存 scratch 路径并补写 release，也不等待任务停止。结果是：

- 若 Hook 父进程已被记录，单独杀父 PID 可能仍留下其当前 `sleep`；
- 若 Hook 父进程尚未被记录，守卫只保留其 child 的 guest PID，不能通过该 child 的 PID 推导父 Hook 的精确身份；
- 删除临时目录不等于进程退出，等待循环可能遇到 Hook 五秒超时／清理路径，但这依赖生产超时，不是测试守卫自身的有界回收。

因此“重新映射 child 并杀死它”不能替代 Hook 父进程和当前同组后代的完整回收。

**问题三：中止任务没有收尾**

`JoinHandle::abort` 只请求取消，不是任务已经停止的同步证明。当前 Drop 不 await 被取消任务；在 runtime 随后展开的情况下，任务通常随 runtime 关闭，但守卫本身没有建立这一顺序。采样循环还执行同步文件和 `/proc` 操作，取消点之后的短窗口仍可能存在。该问题与前两项共同说明资源所有权尚未闭合，不要求把它夸大为已观察到的无限后台线程。

**实际行为边界**

- 本轮正常路径的原生验收 8/8 通过，运行结束后没有发现 fixture 的遗留 shell／`sleep`；因此没有发现正常路径泄漏。
- 上述问题发生在测试失败、panic 或提前展开路径；定级为低等级测试隔离缺口。
- 当前实现没有修改生产进程清理逻辑，不能把本 finding 解读为产品后台命令或插件清理回归。

**建议**

1. 在 fixture 启动时保留其精确进程组身份，并优先按组执行 bounded 清理；若只掌握 child PID，应记录实际父／组身份，而不是假设 child 等于父。
2. 将直接后代及当前子孙纳入测试断言；至少在守卫测试中证明目标组不存在，而不只等待父 shell。
3. 让 Hook release 的所有权独立于可被取消的采样任务，或在失败清理前补写受控 release，再执行进程回收。
4. 在正常 `stop` 与异常展开中使用同一显式任务收尾策略，避免把“abort 已请求”当成“采样已结束”。
5. 保留 PID＋启动时间检查，避免组 ID／PID 重用时误杀不相关进程。

## 3. F-01 修复核实与 Linux 身份边界

### 3.1 四类进程不再相互替代

[`plugin_services.rs:159-175`](../crates/saya-core/tests/plugin_services.rs#L159-L175) 明确定义 `ServerMain`、`ServerChild`、`HookStartedChild`、`HookFinishedChild` 和各自 PID 文件。[`plugin_services.rs:690-707`](../crates/saya-core/tests/plugin_services.rs#L690-L707) 对四个角色逐一执行：

- 必须存在对应 `ProcessIdentity`，缺任一项即 panic；
- 当前启动时间不得仍等于采样值；
- `kill(pid, 0)` 必须失败；
- 错误必须为 `ESRCH`。

这消除了上轮 `observed.len() >= 2` 允许角色互相顶替的问题。

### 3.2 `run.finished` 已进入宿主观察窗口

采样器在独立 Tokio 任务中轮询 ViewPool，而不是依赖 `FixtureModel::start`。两个 Hook 的后代使用不同文件名；Hook 父进程创建后代后等待对应 release，采样器只有在该角色已取得宿主 PID 和启动身份后才写 release。

因此顺序变为：

1. Hook 创建后代并发布 guest PID；
2. 宿主采样器映射 PID、读取启动身份并记录角色；
3. 宿主写 release，Hook 才可退出；
4. 运行及 Hook 清理完成；
5. 测试逐一检查精确身份已经消失。

即使事件发生在最后一次模型调用之后，也不再依赖另一次模型调用采样。独立 stop 先请求采样任务结束并 await，然后读取快照，正常路径时序明确。

本轮真实原生测试 `native_run_calls_plugin_mcp_and_hooks_and_releases_all_views` 通过，两个 Hook journal 均要求 `Succeeded`＋`Cleaned`，四角色断言也实际执行。**macOS 主路径的 F-01 可以关闭**；F-04 只影响异常展开的完整性，不推翻该正常路径证据。Linux 的身份映射仍需按 F-05 修正后才能给出同等结论。

### F-05 低（Linux 测试身份）：guest→host PID 映射未绑定目标 namespace，可能把其他独立环境的同号进程当作目标

[`plugin_services.rs:85-94`](../crates/saya-core/tests/plugin_services.rs#L85-L94) 只要求 `NSpid` 后缀包含给定 guest 数值；[`plugin_services.rs:130-147`](../crates/saya-core/tests/plugin_services.rs#L130-L147) 遍历整个 `/proc` 并接受第一个匹配对象，没有 namespace inode、父子血缘、view/environment ID 或角色条件。

生产准备链 [`runtime_plugins.rs:887-942`](../crates/saya-core/src/runtime_plugins.rs#L887-L942) 分别准备服务和每个 Hook；[`runtime_plugins.rs:622-624`](../crates/saya-core/src/runtime_plugins.rs#L622-L624) 每次独立调用 `execution::prepare`。Linux 的独立 PID namespace 可以合法地同时具有相同 guest PID，例如服务和两个 Hook 的子进程都为 PID 7。

此时采样器可能把另一个 namespace 的同号宿主进程记录为 `server-child` 或某个 Hook child。启动时间只能防止同一宿主 PID 被重用，不能区分同时存活的同号 guest PID。若被误记对象在运行结束时不存在，最终 ESRCH 断言仍可通过，而真正的目标后代可能未被验证；release 也可能在错误身份记录后提前发出。

这是 Linux 验收身份缺口，不是已证明的生产隔离或清理失效。本机 macOS 没有该 guest→host 映射，8/8 通过不能覆盖此问题。建议由宿主在创建环境时保存 namespace／cgroup／父子血缘身份，并将映射约束到该精确环境；没有唯一匹配时应失败，不能取 `/proc` 顺序中的第一个对象。

## 4. F-02 与 F-03 修复核实

### 4.1 F-02 已有实质改进，但未完整关闭

新增实现相较上轮具有以下改进：

- `ProcessIdentity.started` 改为必填，避免没有启动身份也进入精确清理；
- `pending` 先保存原始 guest PID，映射失败不会丢失后续补救线索；
- Drop 对仍未映射的 pending PID 再次尝试宿主映射；
- `cleanup_processes` 只向启动身份仍匹配的 PID 发信号，并设置两秒观察期限；
- 新单测实际启动 shell，证明父进程被杀死且其身份消失。

这些改动证明“已记录单进程的 best-effort 清理”存在，但不是 F-02 所要求的测试资源全生命周期回收。剩余问题按 F-04 保留，不能将进度文档中的“F-02 已修复”扩展解释为任意失败路径均已验证。

### 4.2 F-03 已关闭

[`terminal.rs:520-525`](../crates/saya-tui/tests/terminal.rs#L520-L525) 在 `stalled` 报告之后重新创建 `resume_deadline`。父进程 resume 阶段现在拥有完整五秒预算，不再被 start 等待和填队耗时消耗。

原 start 等待仍有独立期限，填队仍受单帧 I/O 预算和最多 2048 次绘制约束。该修改直接消除上轮指出的共享绝对期限问题，没有改变生产绘制逻辑。本轮完整 TUI 终端测试及 release PTY 旅程通过。
