# 提示词能力改进：DeepSeek 多轮与缓存验证报告

**日期：2026-11-11**

**状态：已完成本机多场景、多轮、多组对照及两轮缓存优化复测。结果仅适用于本次 `deepseek-flash` 服务与这些场景，不代表跨模型、其他服务或全部任务的普遍提升。**

**后续95%目标与工具错误联合验证见[缓存95%联合报告](prompt-cache-95-2026-11-11.md)；本文件保留前一阶段证据。**

## 目的与范围

本轮验证两类改动：

1. 提示词、工具 schema 与错误恢复提示能否减少实际工具调用失败，并保持任务验收结果。
2. 稳定系统前缀能否提高服务端上下文缓存命中率，并量化每轮及整体 token 消耗。

验收不采用模型自述，而使用最终文件、实际工具调用、运行终态和 provider 返回的用量字段。每次运行都有独立临时工作区和 HOME，测试配置显式拒绝 `exec`，不会执行模型生成的命令。任务文本与样例文件会发送到所选服务并产生实际 token 消耗；本地报告不保存真实凭据或模型回复正文。

## 缓存优化内容

修改前，动态系统上下文在每次模型请求时按秒采样时间，并包含工作区路径。在 Chat Completions 的实际请求顺序中，系统文本之后还有约26个工具 schema，再之后才是历史消息；因此后续请求的时间变化会使其后的工具 schema 和历史前缀都无法复用服务端缓存。

缓存优化版采用以下顺序与稳定性约束：

- 运行创建时对时间按分钟对齐，同一 Runtime 的后续模型轮次复用该时间快照。
- 工作区继续由 `runtime_context` 数据项提供，不在动态系统前缀中重复。
- 执行环境事实和宿主 checkpoint 标志位于 `Dynamic request context` 之前。
- 静态指令、工具 schema 与历史消息仍按各 provider 既有协议发送；没有声称客户端能保证服务端命中。

`Usage.cached_input_tokens` 采集 provider 实际返回值；本报告使用 DeepSeek 的缓存用量字段，而不是本地估算。

## Token 计算口径

- `input_tokens`：所有成功模型请求的输入 token 合计。
- `cached_input_tokens`：provider 报告的缓存命中输入 token 合计。
- `uncached_input_tokens = input_tokens - cached_input_tokens`。
- `total_tokens = input_tokens + output_tokens`。
- `cache_hit_rate_pct = cached_input_tokens / input_tokens × 100%`。
- Turn 1 与各运行的后续请求分别汇总；每次运行都是独立进程和工作区，但同一服务可复用共同的静态前缀。
- 输入／输出占比以 `total_tokens` 为分母；缓存／未缓存总消耗占比也以 `total_tokens` 为分母，而不是以输入为分母。
- 百分比保留两位小数，逐项舍入后合计可能为99.99%或100.01%。

## 缓存命中率与 Token 占比

“Turn 1／Turn 2+”单元格为“缓存输入／该阶段输入（命中率）”。最后两列分别是“输入／输出占总 token”和“缓存／未缓存输入占总 token”。

| 组别 | 整体缓存命中率 | 未缓存输入率 | Turn 1 | Turn 2+ | 输入／输出占比 | 缓存／未缓存总消耗占比 |
| --- | ---: | ---: | --- | --- | --- | --- |
| `prompt-only` | 36.37% | 63.63% | 105,472／268,650（39.26%） | 325,504／916,260（35.53%） | 98.16%／1.84% | 35.70%／62.46% |
| `cache-opt-b1` | 83.29% | 16.71% | 105,856／267,433（39.58%） | 1,679,104／1,875,512（89.53%） | 98.84%／1.16% | 82.33%／16.51% |
| `cache-opt-b2` | 83.95% | 16.05% | 106,368／267,511（39.76%） | 941,312／980,460（96.01%） | 98.18%／1.82% | 82.42%／15.76% |
| 缓存优化合并 | **83.54%** | **16.46%** | **212,224／534,944（39.67%）** | **2,620,416／2,855,972（91.75%）** | **98.60%／1.40%** | **82.36%／16.23%** |

与 `prompt-only` 相比，缓存优化合并组的整体缓存命中率提高 **47.17 个百分点**，Turn 2+ 提高 **56.22 个百分点**。Turn 1 两组约为39%，主要反映独立运行间共同前缀的服务端复用；缓存优化的直接目标是避免后续轮次被动态时间截断。

缓存 token 仍是模型输入的一部分，不等于没有消耗资源，也不代表相同数量的免费 token。本报告没有把缓存命中率换算成费用或时延。
