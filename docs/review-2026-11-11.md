## 2. 总体结论

原提交实现了完整的入口和持久化骨架，但多项核心契约没有形成底层不变量。确认 15 项问题，涉及未确认计划执行、未知副作用重放、证据类型与生命周期绕过、单次授权跨 Run 重用、租约丢失后的并发、PLAN 写入、预算失效和终端输出安全。

这些问题不能由“1414 项 Rust 测试通过”抵消：原测试主要覆盖正常生命周期和手工构造的存储状态，没有覆盖本报告中的反例。整改以共享 core／app 层为主，CLI 与 TUI 只保留入口适配，避免在界面上局部掩盖状态机问题。

## 3. 关键复现

以下复现均使用原提交验收记录对应的 release 程序，SHA-256 为 `bd24cedf78d235edcf5b07e63b4575243edb4a86c8ea7562399d79feeb6e32c2`。模型交互使用本机受控 HTTP 替身，所有文件均位于临时目录。

1. **计划确认绕过**：`create → plan → pause → resume` 后，状态由 `waiting / plan_confirmation` 变为 `ready`，`wait_reason=null`。
2. **零步骤完成**：仅有 acceptance 的 Draft 在一次人工核验后成为 Completed，Step 数为 0。
3. **取消后复活**：已完成步骤但等待验收的 Goal 先 cancel，再 verify，最终状态从 Cancelled 变为 Completed。
4. **文件证据绕过**：目标文件不存在且声明摘要不符时，人工文字核验仍写入 Manual evidence 并完成 Goal。
5. **PLAN 写库**：在 PLAN 模式将 `--data-dir` 指向工作区内，执行只读语义的 `goal list` 实际创建 `goals/goals.sqlite3` 并退出 0。
6. **模型预算超限**：`max_model_requests=1` 被规划消耗后，`goal continue` 仍产生第二次 HTTP 请求，记录 usage 为 2 后才进入 LimitReached。
7. **文件核验提前中断**：两步计划约定第二步生成验收文件，自动启动在第一步后因文件尚不存在退出 2；仅产生一次模型请求，第二步保持 Pending。

## 4. 整改原则

1. 未确认、未执行、已取消和结果未知的 Goal 不得通过核验旁路进入执行或完成状态。
2. 证据类型、路径、摘要和验收项必须在 core 模型层匹配；最终完成前重新核验所有文件条件。
3. 文件尚未满足属于正常的待验收状态，不应阻断后续 Step；最终未满足时应保留明确的重验入口。
4. 运行／存储结果缺失一律不作“已持久化”解释；未知副作用继续禁止自动重放。
5. 预授权只对第一个显式 Run 可用，续期失败或用户取消必须传播到 Runtime 取消边界。
6. 所有非 Run Goal 预算在 dispatch 前统一检查；成功调用的 token usage 缺失按保守策略处理。
7. PLAN 的存储与报告发布同时保护当前工作区和 Goal 工作区，模型正文沿用既有终端安全投影。
8. 文件读取以实际读取字节数为最终边界，不能仅依赖打开时的 metadata。

## 6. 整改核实

### 6.1 实现处置

| 编号 | 实际修复 |
| --- | --- |
| F-01 | `GoalRunSummary::from_result` 只在 persistence 明确存在且 `saved=true` 时视为已保存；缺失状态进入 unknown 等待，不能自动重规划 |
| F-02 | Pause 保留等待原因；Resume 按 PlanConfirmation、Verification、Unknown、失败和预算恢复相应状态，不再一律 Ready |
| F-03 | core 校验 evidence 的 kind、路径和摘要与 VerificationSpec 匹配；文件条件的 verify 只执行主机读取，不接受人工摘要或模型裁决 |
| F-04 | 证据发布要求有效计划、无活动 Step 及允许的 Ready／Waiting 状态；人工证据还要求全部 Step 完成并等待验收；Completed 额外拒绝空 Step 集 |
| F-05 | 自动循环只在第一个 Run 构造时读取 approval file，后续 Run 不重新载入已消费授权 |
| F-06 | 心跳续期失败立即调用当前 Run 的共享取消句柄，再等待 Runtime 收尾；结果仍按持久证据保守处理 |
| F-07 | CLI 与 TUI 打开 GoalStore 前均执行当前工作区的 PLAN 根检查；工作区内 data dir 在创建数据库前拒绝 |
| F-08 | 全部 Step 完成后重新检查所有文件条件；失败时移除旧文件证据，成功时以新观测替换，完成只随证据事务发布 |
| F-09 | 中间 Step 的文件缺失／摘要不符按暂未满足处理，不再终止后续调度；最终未满足保持 Waiting，可由 verify 重验 |
| F-10 | begin_dispatch 统一调用完整预算判断，手动 continue、自动启动和 worker 使用同一限制 |
| F-11 | 新增向后兼容的 `token_usage_unknown`；成功规划／Run／人工核验缺少完整 token usage 时停止新 Step，失败 Run 的有限重规划单独分类 |
| F-12 | 活动 Goal 接受持久暂停／取消意图；执行侧轮询控制状态并传播取消，完成或崩溃恢复不会把 Cancelled 覆盖成普通失败 |
| F-13 | Goal 最终文本复用 `safe_output`，清洗终端控制字符并应用当前凭据脱敏 |
| F-14 | 报告相对路径先按 config.cwd 解析，再调用 `publish_session` 同时保护当前和 Goal 工作区 |
| F-15 | SHA-256 读取使用 32 MiB＋1 的实际字节边界；FileExists 只检查普通文件身份，不再无意义读取全文；plan-file 同样增加实际读取上限和 O_NONBLOCK |

### 6.2 新增回归

- Goal core 由 8 项增加到 14 项：覆盖确认状态恢复、非法证据生命周期、缺失 persistence、token 未知及旧记录兼容、全预算 dispatch、活动暂停／取消和增长读取上限。
- Goal CLI 由 7 项增加到 15 项：新增 PLAN 写库、规划预算、Draft／Cancelled、文件创建／变更／重验、跨 Run 预授权、PLAN 双工作区报告、终端控制字符和真实活动 Run 取消。
- 活动取消用例使用 gated 本地 HTTP 请求：另一进程执行 `goal cancel` 后，运行进程必须在响应仍未发布时自行退出 130，数据库保持 Cancelled。
- 文件用例使用真实 `write_file` 工具：第一步无文件不中断，第二步创建后形成证据，第三步修改后旧证据失效；恢复声明内容后，无模型主机核验完成 Goal。
- 预授权用例让两个 Step 请求同一命令；仅第一个 Run 可写标记，第二 Run 回到审批边界，不能复用文件授权。
