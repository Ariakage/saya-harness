### P1

#### R-01 钉住会话的提示被转向注入另一客户端的活动 Run

- **位置**：[service.rs](../../crates/soyo-host/src/service.rs) L687–L776（`submit_prompt`）；[backend.rs](../../crates/soyo-tui/src/controller/backend.rs) L326–L344（TUI `steer`）；[useAppStore.ts](../../desktop/src/store/useAppStore.ts) L754–L765。
- **问题**：`HostService` 只有一个 `prepared` 会话和一个 `active_control` 槽位，被所有客户端共享。`submit_prompt` 只在 `active_run_id.is_none()` 时检查 `session_id` 钉住（L693）；只要有任何 Run 在执行，就直接走“转向”快速路径（L736–L776），把文本 `steer` 进当前 Run，不比较 `params.session_id` 与该 Run 的会话。`SubmitPromptParams.session_id` 的文档注释承诺“不同的 prepared 会话以 `session_changed` 拒绝，而不是静默写入错误会话”，实现只覆盖了空闲情形。
- **复现**（`target/review/r19/steer_repro.py`）：客户端 B 在工作区 B 建会话 Y；客户端 A 在工作区 A 建会话 X 并提交提示，模型请求被替身挂起；B 以 `session_id = Y` 提交 `SECRET-B: …`。结果：B 收到 `{"action":"steered","session_id":"<X>"}`；放行后第 2 次模型请求同时含 `SECRET-B` 与工作区 A 的上下文；会话 X 的历史中持久化了该文本。
- **影响**：TUI、`soyo chat`、桌面端和 `soyo run --interactive` 共用一个 helper。一个终端里输入的指令可能被另一个窗口、另一个工作区的 Run 执行，敏感内容也会写进错误的会话。客户端收到 `steered` 时副作用已经发生；桌面端还会把自己的 `sessionId` 切到对方会话（useAppStore.ts L758）。
- **建议**：在转向前比较目标会话：请求带 `session_id` 且与活动 Run 的会话不一致时返回 `session_changed`／`run_active`，不转向。长期需确认 helper 的多客户端模型：要么按会话维护独立的 prepared／active 槽位，要么让每个 Run 绑定发起连接并只允许该连接转向。补充多客户端回归测试。
- **验证状态**：已复现。

#### R-02 客户端断开后 Run 继续执行；取消与审批不区分请求归属

- **位置**：[server.rs](../../crates/soyo-host/src/server.rs) L168–L202（`handle_client`）、L186–L189（`CancelRequest`）；[service.rs](../../crates/soyo-host/src/service.rs) L1303–L1313（`cancel_run`）、L1315 起（`reply_approval`）。
- **问题**：
  1. `handle_client` 收集了 `streaming_ids`，但断线时只执行 `let _ = streaming_ids;`（L202），不取消该连接发起的 Run。[桌面端设计](../desktop.md)「Helper 后端与 IPC 契约」第 7 点要求“消费者断开或前端取消时立即触发 `RunCancellation`”。
  2. `CancelRequest { id }` 忽略 `id`，直接调用全局 `cancel_run()`（L186–L189），`cancel_run` 方法同样无参数。任一客户端的 Ctrl-C、Esc 或停止按钮都会取消别的客户端的 Run。
  3. `reply_approval`／`reply_input` 只校验 `approval_id`／`call_id`，不校验应答来自发起 Run 的连接。
- **复现**（`target/review/r19/config_kill_repro.py` 第二部分）：经 helper 执行 `soyo run --permissions bypass`，模型请求挂起时对 CLI 进程发 SIGKILL，再放行；模型随后返回的 `exec` 照常执行，标记文件在客户端死亡后创建，helper 仍在运行。SIGINT／SIGTERM／SIGHUP 会被转发为 `cancel_run`，但 SIGKILL、崩溃、终端断连、socket 写失败都不会。
- **影响**：改用 helper 之前，杀掉 `soyo run` 进程就等于停止 Agent；现在 Agent 会在无人观察的情况下继续调用工具。Run 若停在审批或澄清上，会无限期占住 helper 唯一的 Run 槽位和会话锁，其他客户端只能看到 `run_active`。
- **建议**：为每个 Run 记录发起连接和请求 id；连接关闭时取消其 Run 并让挂起的审批／澄清以拒绝收口；`CancelRequest` 按 id 定位；审批应答校验连接归属。补充“客户端断开即取消”的回归测试。
- **验证状态**：断开后继续执行已复现；跨客户端取消与审批为代码阅读。

#### R-03 helper socket 没有访问控制

- **位置**：[server.rs](../../crates/soyo-host/src/server.rs) L56–L74（删除旧 socket、`create_dir_all`、绑定）、L131–L137（pid 文件）、L253 起（`dispatch` 方法表）；[socket.rs](../../crates/soyo-ipc/src/socket.rs) L35–L46。
- **问题**：`~/.soyo` 用 `create_dir_all` 按进程 umask 创建，socket 由 `ListenerOptions` 按 umask 创建，之后没有 `chmod 0700/0600`，也没有用 `getpeereid`／`SO_PEERCRED` 校验对端 uid。连上的任何进程都可以调用 `set_permission_mode`（`bypass`）、`set_sandbox_backend`、`submit_prompt`、`reply_approval`、`import_credential`、`export_session`（写入任意 `target_path`）、`stage_attachments`／`set_avatar`（读取任意文件并经 `fetch_attachment`／`get_desktop_prefs` 取回）、`set_global_prompt`（持久改写全局指令）和 `Shutdown`。仓库其他私有存储都经 `soyo-fs` 强制 0700／0600 并校验属主，helper 是唯一例外。
- **复现**（`target/review/r19/socket_repro.py`）：umask 002 下启动 helper，目录为 `0775`、socket 为 `0775`、`helper.pid` 为 `0664`；未经任何认证的客户端调用 `set_permission_mode {"permissions":"bypass"}` 返回成功。
- **影响**：默认 umask 022 时其他用户没有 socket 写权限，无法连接。umask 002／007 的多用户环境（共享开发机、按组协作的 Linux 主机）中，同组用户可以用受害者身份以 `bypass` 运行任意命令、读取任意文件。沙箱内命令在 macOS 实测无法连上，见 P0 一节。
- **建议**：创建 `~/.soyo` 时强制 0700 并校验属主（复用 `soyo_fs::ensure_root_dir`），绑定后把 socket 设为 0600；accept 后校验对端 uid 与 helper 相同；pid 文件按 0600 原子写入。Windows 命名管道需设置仅当前用户的 DACL，见 R-14。
- **验证状态**：已复现（权限位与未认证调用）。

#### R-04 经 helper 执行时静默改用 helper 的配置与环境

- **位置**：[main.rs](../../crates/soyo-cli/src/main.rs) L611、L1103、L1514、L1530（是否走 helper 只看 `--config`／`--data-dir`）；[service.rs](../../crates/soyo-host/src/service.rs) L302–L330（`from_environment` 只在 helper 启动时读取一次）；[client.rs](../../crates/soyo-ipc/src/client.rs) L384–L401（子进程继承拉起者的环境与 cwd）。
- **问题**：helper 的 `Config` 和 `Environment` 来自第一个拉起它的客户端，此后不再变化。CLI／TUI 是否走 helper 只判断两个命令行参数，不比较 `SOYO_CONFIG`、`XDG_CONFIG_HOME`、`XDG_DATA_HOME`、`HOME`、API 密钥、代理变量和 `PATH`。`RunPromptParams` 也不传调用方环境。
- **复现**（`target/review/r19/config_kill_repro.py` 第一部分）：helper 以 `SOYO_CONFIG=a.toml` 启动，再执行 `SOYO_CONFIG=b.toml soyo run …`：退出码 0，请求发往 a 的模型端点（A 1 次、B 0 次）。
- **影响**：用环境变量选配置、轮换密钥、用 direnv／venv 切换 `PATH` 或代理的用户，会在不知情时用错误的模型、密钥、数据目录执行。工具子进程继承的也是 helper 的环境：从 Finder 启动的桌面端拉起 helper 时 PATH 只有 `/usr/bin:/bin:/usr/sbin:/sbin`，之后终端里的 `soyo` 也会继承这套环境。D-074 宣称“逐字节兼容”，但执行环境语义已经改变。
- **建议**：让客户端在请求中携带配置指纹（配置路径、数据目录、相关环境变量名与值的哈希），与 helper 不一致时回退进程内执行或明确报错；`exec` 的继承环境按请求方传递，或在文档中明确改为 helper 环境并给出提示。需项目负责人确认契约。
- **验证状态**：已复现（配置分歧）；环境继承为代码阅读。

#### R-05 首次启动 helper 即让旧用户的全局记忆“消失”

- **位置**：[config.rs](../../crates/soyo-core/src/config.rs) L643–L662（`memory_root`：`~/.soyo` 是目录就优先使用）；[server.rs](../../crates/soyo-host/src/server.rs) L59–L63（helper 无条件 `create_dir_all(~/.soyo)`）。
- **问题**：更名契约是“`.soyo` 优先、`.saya` 回退”，回退条件是 `~/.soyo` 不存在。helper 的 socket、pid、env、桌面偏好都放在 `~/.soyo`，TUI、chat、resume 和桌面端启动时都会自动拉起 helper，于是 `~/.soyo` 一定会被创建，回退随之失效。
- **复现**（`target/review/r19/memroot_repro.py`）：临时 HOME 只有 `~/.saya/MEMORY.md`。启动 helper 前，`soyo memory settings` 报告根为 `~/.saya`；启动并停止 helper 后，同一命令报告根为 `~/.soyo`。
- **影响**：所有从 Saya 升级的用户在第一次打开 TUI 或桌面端后，全局记忆不再被读取和注入，新记忆写进另一个目录，形成两份分叉的记忆库。数据没有被删除，但用户不会收到任何提示。
- **建议**：把 helper 运行时文件移到独立目录（例如 `state_dir/helper` 或 `~/.soyo/run`），并把记忆根的判定改为“`~/.soyo` 下存在记忆文件”，而不是“目录存在”；或在首次创建 `~/.soyo` 时执行一次显式迁移并提示用户。补充升级回归测试。
- **验证状态**：已复现。

#### R-06 API 密钥明文写入未受保护的 `~/.soyo/env`

- **位置**：[envfile.rs](../../crates/soyo-host/src/envfile.rs) L1–L8（设计说明）、L28–L30、L65–L117；[lib.rs](../../crates/soyo-app/src/lib.rs) L466–L546（受保护路径与私有路径集合，不含 helper 目录）；[prefs.rs](../../crates/soyo-host/src/prefs.rs) L16–L22、L127–L129。
- **问题**：首次运行向导把密钥值写入 `~/.soyo/env`（0600），helper 启动时把它并入 `Environment`。但该文件以及同目录的 `helper.sock`、`helper.pid`、`desktop_prefs.json`、全局指令 `AGENTS.md` 都不在文件工具的私有路径和沙箱受保护路径中。D-072 第 (4) 条要求凭据“仅走 `SecretRegistry` 与宿主私有存储”，基线要求 `config.toml` 只引用变量名；这里新增了一份位于保护模型之外的明文密钥存储。
- **复现**（`target/review/r19/envfile_repro.py`）：工作区 = HOME、默认 `auto` 模式下，模型先 `read_file ~/.soyo/env`，读到完整内容（`OPENAI_API_KEY=sk-test-value`），再带 `expected_version` 调用 `write_file` 追加 `HTTPS_PROXY=http://127.0.0.1:9`，写入成功。对照：工作区为 HOME 子目录时，`bypass` 下的同一写入因越出根目录被 EPERM 拒绝。
- **影响**：工作区为 HOME 或额外根包含 `~/.soyo` 时，模型可以读取明文密钥，也可以向 helper 的环境植入代理、证书等变量；这些变量在下次启动 helper 后作用于所有客户端的模型请求。读取输出的脱敏只覆盖当前配置引用到的变量；本次复现的配置未引用该变量，值原样出现在模型可见的工具结果中。
- **建议**：密钥改存现有 `FileCredentialStore`（或 `state_dir` 下 0700 私有目录），不放在记忆根目录；把 helper 目录整体加入 `private_paths` 与 `sandbox.protected_paths`；向导写入后立即把值注册进 `SecretRegistry`。

#### R-07 桌面安装包不含 helper 程序

#### R-08 桌面端 helper 连接只初始化一次

- **位置**：[client_state.rs](../../desktop/src-tauri/src/client_state.rs) L52–L75。
- **问题**：`DesktopState.client` 是 `OnceCell<Arc<HelperClient>>`，首次成功后不再重建。helper 因 `soyo kill`、崩溃、R-12 的挤占、socket 看门狗退出，或被 CLI 的版本检查回收（`connect_checked` 发现 helper 空闲且程序路径或版本不同时重启它：非交互调用方静默重启，交互调用方确认后重启）而断开后，客户端读循环以 `helper_disconnected` 收口，之后每个命令都写入已关闭的连接。前端没有重连逻辑（未搜到 `helper_disconnected` 处理）。

#### R-09 NDJSON 帧上限在整行读入内存后才检查

- **位置**：[framing.rs](../../crates/soyo-ipc/src/framing.rs) L18–L49。
- **问题**：`read_line` 会一直读到换行符，读完后才判断 `line.len() > MAX_FRAME_BYTES`，因此 8 MiB 上限并不限制内存。helper 读客户端帧、客户端读 helper 帧都有这个问题。
- **复现**（`target/review/r19/socket_repro.py`）：连接后发送 128 MiB 不含换行的数据，helper RSS 从 23.9 MB 增至 157.1 MB（+130 MiB）。
- **影响**：任何能连上 socket 的进程都能让 helper 占用任意多内存直至被系统终止，同时中断所有客户端的 Run。
- **建议**：用 `take(MAX_FRAME_BYTES + 1)` 包装读取或用 `fill_buf` 逐块扫描，超限立即断开连接；补充超长帧测试。
- **验证状态**：已复现。

#### R-10 `fetch_attachment` 每次请求泄漏内存

- **位置**：[attachment.rs](../../crates/soyo-host/src/attachment.rs) L253–L262（`split_uri` 中 `Box::leak`）。
- **问题**：为返回 `&'static str`，每次解析 URI 都把路径部分泄漏到进程生命周期。桌面端每次预览图片都会调用。
- **复现**（`target/review/r19/attachment_repro.py`）：80 次 2 MiB 路径的 POST（在 `split_uri` 前就返回 405）之后，RSS 稳定在 38.9 MB；随后每 40 次 2 MiB 路径的 GET 使 RSS 增加约 83 MB（122.1 MB → 205.3 MB），不会回收。
- **影响**：helper 是常驻进程，正常使用时内存缓慢增长；配合 R-09，任一客户端都可以快速耗尽内存。
- **建议**：让 `split_uri` 返回 `String` 或借用输入切片，去掉 `Box::leak`。
- **验证状态**：已复现。

#### R-11 媒体引用解码错误，桌面端会话媒体预览不可用

- **位置**：[attachment.rs](../../crates/soyo-host/src/attachment.rs) L231–L250（`percent_decode` 的高、低半字节都读 `bytes[i + 2]`）；[AttachmentPreview.tsx](../../desktop/src/components/AttachmentPreview.tsx) L70（前端用 `encodeURIComponent` 编码 `ref`）；[service_tests.rs](../../crates/soyo-host/src/service_tests.rs) L592（测试传入未编码的 `ref`，掩盖了问题）。
- **复现**（`target/review/r19/attachment_repro.py`）：同一会话下，未编码的 `ref=soyo-media://obj` 通过解码并返回 404（对象不存在）；前端实际发送的 `soyo-media%3A%2F%2Fobj` 返回 400 `Invalid encoded media reference`。
- **影响**：工具产出的截图等会话媒体在桌面端全部无法预览。只能解出 `0x00, 0x11, …, 0xFF` 这类字节，构造不出 `/` 或 `.`，因此没有路径穿越风险。
- **建议**：高半字节改为 `bytes[i + 1]`；测试改用与前端一致的编码形式，并覆盖多字节 UTF-8。
- **验证状态**：已复现。

#### R-12 helper 绑定时挤掉正在服务的实例

- **位置**：[server.rs](../../crates/soyo-host/src/server.rs) L56–L74、L76–L93（看门狗）、L118–L121（退出时删 pid 文件）。
- **问题**：`run()` 绑定前无条件 `remove_file(socket)`，不先探测已有实例是否存活。第二个 `soyo helper` 会删掉在用的 socket 并绑定新的；原实例的看门狗在 1 秒内发现 `(dev, ino)` 变化并自行关停，执行 `service.shutdown()`，正在进行的 Run 被终止。原实例退出时还会删除 `helper.pid`，而此时 pid 文件已被新实例覆盖。两个客户端同时 `connect_or_spawn`（L59–L74）也会触发同样的竞态。D-073 称“socket 绑定即单例”，实现并不保证。
- **影响**：并发启动 TUI 与桌面端，或用户手动执行 `soyo helper` 时，正在执行的 Run 可能被中断；`soyo kill` 的回退路径读不到新实例的 pid。
- **建议**：绑定前先尝试连接，能收到 `Hello` 就退出；用 `~/.soyo` 下的 `flock` 锁文件做单例；pid 文件只在内容仍是自己的 pid 时删除。
- **验证状态**：代码阅读。

#### R-13 `soyo kill` 回退路径不校验进程身份

- **位置**：[helper_commands.rs](../../crates/soyo-cli/src/helper_commands.rs) L37–L56。
- **问题**：socket 不可达时，读取 `helper.pid`，只要 `kill(pid, 0)` 成功就发送 SIGTERM。helper 崩溃后 pid 可能被同一用户的其他进程复用；运行时其他位置用 pid + 启动时间识别进程（`ProcessIdentity`），这里没有。
- **影响**：可能终止编辑器、构建等无关进程，且输出 “soyo helper terminated”。
- **建议**：pid 文件同时记录进程启动时间与程序路径，发信号前校验；或只通过 socket 关闭，socket 不可达时只报告状态、不发信号。
- **验证状态**：代码阅读。
