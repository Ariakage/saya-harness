### P0

#### F-01 默认 `auto` 下文件工具可无审核改写 `.git` 控制文件，导致沙箱外任意命令执行

**位置**

- [`permissions.rs:729-733`](../../crates/saya-core/src/permissions.rs#L729-L733)：文件目标只与显式 host_protected 集合比较。[`permissions.rs:810-826`](../../crates/saya-core/src/permissions.rs#L810-L826)：auto 下，工作区内的本地写工具默认 `Allow`（`native_default`），不经模型核查，也不需要人工确认。
- [`saya-app/src/lib.rs:384-399`](../../crates/saya-app/src/lib.rs#L384-L399)、[`lib.rs:460-469`](../../crates/saya-app/src/lib.rs#L460-L469)：默认保护集合只包含配置、data、state、cache、`.soyo/local`，以及凭据、OutputStore 和记忆文件，不含 `.git`。
- [`execution/seatbelt.rs:93-102`](../../crates/saya-core/src/execution/seatbelt.rs#L93-L102)、[`execution/linux/mod.rs:295`](../../crates/saya-core/src/execution/linux/mod.rs#L295)：工作区作为整体可写根放行，原生隔离同样没有保护 `.git` 控制文件。
- [`tools/write.rs:258-271`](../../crates/saya-core/src/tools/write.rs#L258-L271)：替换已有文件时沿用原权限。已存在的可执行 hook（例如 husky、pre-commit 安装的 hook）被改写后仍然可执行。
- 对照 [`checkpoint/workspace.rs:173-181`](../../crates/saya-core/src/checkpoint/workspace.rs#L173-L181)：检查点子系统已把 `.git` 定义为“仓库控制数据”并拒绝寻址。同一工程对 `.git` 的定位不一致，这类改写也无法被检查点捕获或回滚。

**问题**

git 在 `git status`、`git diff`、`git commit` 等常规操作中，会执行 `.git/config` 里的 `core.fsmonitor`、`core.pager`、`diff.external`、filter driver 等命令，以及 `.git/hooks/*`。VS Code、JetBrains 等 IDE 会在文件变化后自动在后台运行 `git status`。这些文件不出现在 `git diff`／`git status` 的输出里，用户很难察觉。

auto 模式“工作区内读写默认允许”，把这些文件当作普通文件处理。于是一次受提示注入影响的模型调用，就能把“工作区写入”升级为“以宿主用户身份、在沙箱之外执行任意命令”。这同时绕过了 exec 的独立模型核查和 D-040／D-050 的原生隔离。

**复现**（当前提交的 debug 程序，所有文件位于临时目录）

1. 本地 OpenAI 兼容替身先返回 `read_file .git/config`，再返回带 `expected_version` 的 `write_file .git/config`，内容追加 `[core] fsmonitor = "touch <临时目录>/escaped-marker"`。
2. 执行 `saya --mode work --permissions auto --output json run ...`，使用默认原生隔离，未配置任何权限规则。
3. 结果：退出码 0，`status=completed`，共 3 次模型请求，没有核查或确认。`write_file` 返回 `{"ok":true,...,"created":false}`。
4. 之后在工作区执行一次普通 `git status`（git 2.54.0），标记文件被创建。

**建议**

1. 文件工具层：对每个可写根内的 `.git` 控制路径默认拒绝写入，三种权限模式（含 bypass）都生效，语义与现有 host_protected 一致。至少覆盖 `config`、`hooks/**`、`info/**`、`modules/**/config`、`modules/**/hooks/**`，以及 `.git` 为 worktree 文件时其指向的 gitdir 中的对应路径。定义与检查点保持一致。
2. 原生隔离层：Seatbelt 在 profile 末尾追加 deny，Bubblewrap 使用只读重绑定，并沿用现有“缺失保护路径”的处理方式覆盖尚不存在的路径。如需保留 Agent 执行 `git commit` 的能力，可以只保护 config 和 hooks，不保护 objects、refs、index。
3. 回归测试：在 auto、manual、bypass 下，覆盖 `write_file`／`edit_file`／`apply_patch` 写 `.git/config` 和已有可执行 hook 的情况，以及沙箱命令写入被拒的情况；同时覆盖 `.git` 为 worktree 文件的情况。
4. 该调整会改变默认权限契约。按 AGENTS.md，需项目负责人确认后再写入决策记录，并同步 `sandbox.md`、`execution.md`、`configuration.md`。工作区为 HOME，或 `additional_roots` 覆盖 HOME 时，shell rc、`~/.ssh`、`~/.gitconfig` 等同样会被隐式执行的文件也宜纳入保护。

### P2

#### F-02 Anthropic 流式解析按二次复杂度累积 text／thinking

**位置**：[`provider/anthropic.rs:944-948`](../../crates/saya-core/src/provider/anthropic.rs#L944-L948)。每个 `text_delta`、`thinking_delta`、`signature_delta` 都执行 `format!("{previous}{text}")`，重建整段字符串并重新插入 JSON 对象。单条响应上限为 `MAX_OUTPUT_BYTES = 16 MiB`（[`anthropic.rs:20`](../../crates/saya-core/src/provider/anthropic.rs#L20)）。同仓的 Chat（`chat.rs:506`）和 Responses（`responses.rs:614/644/852`）适配器都是原地 `push_str`。

**影响**：总拷贝量与累积长度的平方成正比。下表为独立 release 微基准的结果（serde_json 1.0.154，完全复刻上述写法，每个 delta 20 字节）：

| 累积文本 | delta 数 | 当前实现 | 原地追加 |
| --- | --- | --- | --- |
| 256 KiB | 13,107 | 102.9 ms | 0.03 ms |
| 1 MiB | 52,428 | 1.09 s | 0.12 ms |
| 4 MiB | 209,715 | 39.3 s | 0.72 ms |

CLI 运行在 current_thread 运行时上（见 F-03），解析期间 TUI 绘制、流空闲计时和取消处理都会停顿。所有 `anthropic-messages` profile 都受影响，包括兼容网关。长 thinking（`adaptive`）或较大的 `max_output_tokens`（D-054 硬上限 1,000,000）下最明显。

**建议**：在 `Block` 中用 `String` 缓冲 text、thinking、signature（与现有的 `arguments` 相同），在 `content_block_stop` 时一次性写回 JSON；或对 `Value::String` 原地 `push_str`。补充大量 delta 的回归测试，断言结果一致。

#### F-03 单线程运行时上执行长时同步工作，期间取消与界面停顿

**位置**

- [`saya-cli/src/main.rs:1093`](../../crates/saya-cli/src/main.rs#L1093) 使用 `#[tokio::main(flavor = "current_thread")]`。SIGINT、TERM、HUP 由同一运行时上的任务监听（[`signals.rs:34-46`](../../crates/saya-cli/src/signals.rs#L34-L46)）。
- [`browser/worker/environment.rs:651-679`](../../crates/saya-core/src/browser/worker/environment.rs#L651-L679)：`async fn verify` 直接同步调用 `verify_worker_identity_checked`。该函数对 Node、worker、Chromium 三棵安装树做全量 SHA-256（[`identity.rs:567-690`](../../crates/saya-core/src/browser/worker/identity.rs#L567-L690)），上限为 65,536 项、4 GiB（[`installation.rs:13-14`](../../crates/saya-core/src/browser/worker/installation.rs#L13-L14)）。
- [`browser/worker/provider.rs:147`](../../crates/saya-core/src/browser/worker/provider.rs#L147) 构建 provider 时通过 `preflight()` 做同样的全量校验；[`provider.rs:312`](../../crates/saya-core/src/browser/worker/provider.rs#L312) 在首次启动 worker 前再校验一次。
- [`saya-tui/src/controller.rs:417-476`](../../crates/saya-tui/src/controller.rs#L417-L476)：每次提交都在 `async fn start_run` 内直接调用同步的 `saya_app::build_runtime`。后者会打开多个存储，并在启用 Browser 时执行上述预检。
- 锁获取使用 `thread::sleep` 轮询。例如 `PluginStore::open`（[`plugin_store.rs:320`](../../crates/saya-core/src/plugin_store.rs#L320) → [`plugin_store/disk.rs:76-93`](../../crates/saya-core/src/plugin_store/disk.rs#L76-L93)）在竞争时最长 10 s；`saya-fs::acquire_flock`（[`lib.rs:242-280`](../../crates/saya-fs/src/lib.rs#L242-L280)）的超时由调用方传入，模块存储使用 5 s。

**影响**：启用 Browser 时，每次构建运行时至少做一次安装树全量哈希，首次启动 worker 时再做一次。期间信号监听任务无法运行，Ctrl-C 要等同步段结束后才生效（信号被延迟处理，不会丢失），TUI 也不重绘。另一 saya 进程持锁时同样会停顿。这与 B-08、B-15、B-16 对取消的预期不符。

**建议**：把身份校验和 `build_runtime` 中的阻塞部分移到 `spawn_blocking`，用 `AtomicBool` 等跨线程取消标志驱动现有 checkpoint。对已验证的安装树，按 (dev, ino, size, mtime, ctime) 缓存树级结论，启动前只复核已固定的可执行镜像（这部分已实现）。async 可达路径上的锁轮询改为在阻塞线程执行，或改用 `tokio::time::sleep`。如果 TUI 需要同时处理输入、绘制与后台任务，可评估改用 multi-thread 运行时。

#### F-04 模块开关库首次初始化不是原子操作，中断后所有运行与补救命令都会失败

**位置**

- [`modules.rs:239-286`](../../crates/saya-core/src/modules.rs#L239-L286)：`ModuleStore::open` 先用 `create_or_verify_private_file` 创建 0 字节文件，再配置 WAL 并执行 `initialize_schema`，且只在 `created == true` 时初始化。
- [`modules.rs:397-410`](../../crates/saya-core/src/modules.rs#L397-L410)：文件已存在但长度为 0 时返回 `storage_error`。[`modules.rs:157-191`](../../crates/saya-core/src/modules.rs#L157-L191)：`load_overrides` 对未初始化的库同样失败。
- 调用方：[`saya-app/src/lib.rs:503`](../../crates/saya-app/src/lib.rs#L503)（每次构建运行时）、[`saya-cli/src/main.rs:859`](../../crates/saya-cli/src/main.rs#L859)（TUI 启动）、[`main.rs:982`](../../crates/saya-cli/src/main.rs#L982)（`config check`）、[`module_commands.rs:61-66`](../../crates/saya-cli/src/module_commands.rs#L61-L66)（enable 和 disable 都先调用 `ModuleStore::open`）。

**问题**：首次执行 `saya module … enable|disable` 时，如果在建文件之后、schema 提交之前被中断（Ctrl-C、SIGKILL、ENOSPC、WAL 初始化失败等），会留下 0 字节或没有 `application_id` 的库文件。之后它不会被当作“未初始化”重新建表，也没有任何自动或命令级的恢复路径。

**复现**：在临时 XDG 目录中，创建权限为 0600、长度为 0 的 `data/saya/modules/modules.sqlite3`（所在目录为 0700）。之后：

- `config check` 退出 2；
- 未启用 Browser 的 `run --output json` 退出 2，错误为 `storage_error: module database is empty or corrupt`；
- `module browser disable` 和 `module list` 同样退出 2。

用户只能手工删除私有数据目录中的文件，文档对此也没有说明。

**建议**：持锁时，把“长度为 0”或“application_id、user_version 均为 0 且没有表”的库视为未初始化并完成初始化；或者在临时文件中建好 schema 后再 rename 落位。`module disable` 应能在库不可读时安全重建。对属主、权限、symlink 的检查继续失败关闭。补充初始化被中断的回归测试，并在 `browser.md` 中写明恢复方式。

#### F-05 JSON／JSONL 预备阶段错误被统一改写为 `invalid_input`，契约错误码丢失

**位置**：[`saya-cli/src/main.rs:224-259`](../../crates/saya-cli/src/main.rs#L224-L259) 的 `output_error` 固定输出 `status=failed`、`stop_reason="invalid_input"`、`error.code="invalid_input"`，退出码 2。[`main.rs:1076-1088`](../../crates/saya-cli/src/main.rs#L1076-L1088)：`run` 的所有错误都经由它输出。查询类命令的 `query_error`（[`main.rs:260-271`](../../crates/saya-cli/src/main.rs#L260-L271)）同样固定为 `invalid_query`。

**问题**：B-17 规定退出码 2 只用于“CLI 输入／配置无效”，存储等运行失败应为退出码 1。B-18 和 `execution.md` 规定第二个写入者返回 `session_busy`，损坏的库返回 `storage_corrupt`。而实际输出中，这些代码只作为 message 文本的前缀出现。

**复现**：两个进程写同一会话时，第二个 `run --session ID --output json` 输出：

```json
{"status":"failed","stop_reason":"invalid_input","error":{"code":"invalid_input","message":"session_busy: session is already in use"}}
```

退出码为 2。脚本无法依据结构化字段区分“稍后重试”和“修正配置”，只能解析文本。现有测试只检查文本模式下的 stderr（`tests/cli/recovery.rs:115-117`）。

**建议**：让 `output_error` 接收 `BoundaryError`，保留原始 code（`session_busy`、`storage_error`、`storage_corrupt`、`invalid_config` 等），并按 B-17 区分退出码 1 和 2。补充 JSON／JSONL 下 `session_busy` 和存储失败的用例。

#### F-06 auto 下精确预授权仍先送模型核查，核查结论可推翻用户预授权

**位置**：[`approvals.rs:427-562`](../../crates/saya-core/src/approvals.rs#L427-L562)：先执行 `review_operation`，只有结论为 `Ask` 时（[`approvals.rs:517-522`](../../crates/saya-core/src/approvals.rs#L517-L522)）才查询 `preapproved`。[`review.rs:276-318`](../../crates/saya-core/src/review.rs#L276-L318)：未命中规则的 exec 返回 `ModelReview`，并消耗一次模型请求预算。

**复现**：执行 `--permissions auto run --approval-file`，授权文件精确列出 `["/bin/echo","hello"]` 和工作区 cwd。替身核查返回 `deny` 时，exec 结果为 `permission_denied`，运行仍以 `completed`、退出码 0 结束；替身返回 `allow` 时命令才执行。两种情况都产生 1 次核查请求。

**问题**：B-11 把预授权定义为满足命令确认的显式授权，`usage.md` 只给出了 manual 下的示例。auto 模式下，CI 的结果取决于核查模型的判断：同一授权文件可能这次生效、下次被拒，而且每条命令都额外消耗模型请求预算。

**建议**：请项目负责人确认语义后二选一，并写入文档：

- (a) 在 PLAN、显式 deny、路径根检查之后、模型核查之前，先匹配精确预授权；
- (b) 保持现状，但在 `usage.md`、`execution.md` 中写明“auto 下预授权只替代人工兜底，模型核查的 deny 优先”，并在结果中给出可识别的拒绝来源。

#### F-07 CI 供应链与重复清单

- [`ci.yml:21-24`](../../.github/workflows/ci.yml#L21-L24) 每次运行都执行 `cargo install --locked cargo-audit`，未固定版本。其他步骤都已固定（action 固定到 SHA、工具链固定版本），唯独这里的结果会随上游发布漂移。建议用 `--version` 固定版本，或改用固定 SHA 的 action 并加缓存。
- [`n5-validation.yml:196-197`](../../.github/workflows/n5-validation.yml#L196-L197) 在空项目中用 `npm install --no-save` 安装固定版本的直接依赖，但没有 lockfile，传递依赖会浮动（已使用 `--ignore-scripts`）。建议提交 lockfile 并改用 `npm ci`。
- [`ci.yml:47-60`](../../.github/workflows/ci.yml#L47-L60) 和 [`justfile:56-68`](../../justfile#L56-L68) 各维护一份相同的 12 条工具回归命令，新增脚本时容易漏同步。`justfile` 该任务的注释仍写“发行、N2、N3 与提示词评估”，实际已包含 N5。

#### F-08 模块体量与耦合

- 超过 1,500 行的生产模块：`runtime/mod.rs` 2,589 行、`runtime_services.rs` 1,883 行、`sqlite.rs` 1,876 行、`command_analysis.rs` 1,763 行、`media.rs` 1,631 行、`browser/vm/launcher.rs` 1,601 行、`browser/worker/sandbox.rs` 1,574 行、`browser/state.rs` 1,559 行。最大的测试文件为 `browser/worker/tests.rs`，4,905 行。
- `saya-core` 约 16.3 万行，承担运行时、执行隔离、存储、Browser／VM、MCP、记忆、插件等全部职责。本轮拆分只抽出了 `saya-contract`（657 行）和 `saya-fs`（366 行）。
- 拆分后，`browser/vm/mod.rs`、`browser/worker/mod.rs`、`execution/linux/mod.rs` 用 `pub(in …) use` 集中预导出，共带 28 处 `#[allow(unused_imports)]`。子模块隐式依赖整组导入，死导入不再能被编译器发现。
- 少量生产路径用 `unreachable!()` 表达由调用方保证的不变量。例如 `goal_commands.rs:269` 先接收整个枚举再解构，可改为直接传入已解构的参数。
- 建议：按领域继续拆出 Browser、执行隔离、存储等 crate，至少把 runtime 主循环中的模型轮次、工具调度、续写拆成独立模块；用显式 `use` 替换预导出加 allow 的写法。

#### F-09 预发布 Mermaid 解析器处理模型输出，且没有 panic 隔离

`saya-tui/Cargo.toml` 固定使用 `merman-core = "=0.8.0-alpha.3"`。[`rich_text/mermaid.rs:8-18`](../../crates/saya-tui/src/rich_text/mermaid.rs#L8-L18) 对输入有预算限制，但调用没有包裹 `catch_unwind`。解析器一旦 panic，[`terminal.rs:312-313`](../../crates/saya-tui/src/terminal.rs#L312-L313) 的 hook 只负责恢复终端，整个 TUI 会话随之退出。建议对解析和布局使用 `catch_unwind`，失败时降级为显示源码；或在发布线上换用稳定版本。

## 5. 已核查且未发现问题的边界

- 生产代码：脚本扫描 214 个生产文件（已排除 `#[cfg(test)]` 模块和测试文件），没有 `.unwrap()`／`.expect(`。抽查的外部输入字节切片（记忆分页、OutputStore 截断等）都先校验了 char boundary。
- 权限：PLAN 检查先于规则；优先级为 deny＞ask＞allow；bypass 仍保留显式 deny；存在 `env` 覆盖时，静态 allow 降级为核查。审批绑定 run、session、规范化参数、模式与权限修订号，并在每次 await 后复核；拒绝记忆只限本次 Run。并行只读批处理同样逐条取得一次性许可。
- 文件工具：使用 cap-std 根目录句柄加 `O_NOFOLLOW`，并在打开前后比对 dev／ino；受保护路径按 NFC 加 case-fold 比较；新文件通过 hard_link 实现不覆盖创建。
- Web 读取：每一跳都重新校验 allowlist；DNS 结果须全部满足公网策略，连接固定到已校验的地址；禁用环境代理和自动重定向。IANA 特殊地址（含 IPv4 映射、NAT64、6to4、文档段）均被拒绝。
- Seatbelt：所有路径都以 `-D` 参数传入，不拼接进 SBPL；保护路径的 deny 置于 profile 末尾。VM SSH 远端命令的单引号转义正确。
- 模型适配：SSE 有单事件上限。Anthropic 事件状态机检查索引连续、内容块不重叠、stop reason 与内容一致，截断时不接受半截的工具调用。续写合并后的历史，仍满足 provider 文本块与本地文本的配对校验。
- 会话存储和凭据库的异步接口都经由 `spawn_blocking` 执行。
