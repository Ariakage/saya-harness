## 2. 已确认发现

### R-01 中：持续 `WouldBlock` 会使 TUI 无限重试脏帧，重试前也没有重新同步终端/Ratatui 状态

**位置**

- [`crates/saya-tui/src/controller.rs:999-1017`](../crates/saya-tui/src/controller.rs#L999-1017)：绘制失败后的控制分支。
- [`crates/saya-tui/src/terminal.rs:433-455`](../crates/saya-tui/src/terminal.rs#L433-455)：单帧 250ms 预算与 `try_draw` 调用。
- [`crates/saya-tui/src/terminal.rs:239-279`](../crates/saya-tui/src/terminal.rs#L239-279)：底层非阻塞写入和 `WouldBlock` 返回。
- 锁定依赖 `ratatui-core 0.1.2` 的 `terminal/render.rs:288-308`：先 flush diff，再执行后续 cursor/swap；出错时不能假设此前输出完整。

**问题机制**

`TerminalGuard::draw` 的预算只限制一次 `try_draw`。当 PTY 对端保持打开但持续不读取时，输出队列最终填满，单次绘制在预算到期后返回 `WouldBlock`。控制层命中下面的分支：

```rust
Err(error) if error.kind() == std::io::ErrorKind::WouldBlock => {}
```

该分支保留 `dirty = true`，下一轮继续绘制；没有累计背压时间、连续失败次数上限或总断开判定。因而：

1. 对端持续不读取时，`run_loop` 可以永久重复“等待单帧预算 → `WouldBlock` → 下一帧”。
2. 只有其他非 `WouldBlock` 错误、输入或信号才能结束该状态；持续慢消费者本身不会触发契约所述的取消所属运行。
3. 活跃模型、后台工具和插件可能继续产生实际副作用，而用户失去正常画面、审批详情和状态呈现。它不是 CPU 空转式的 tight loop，但仍是无限生命周期的背压循环。

这与 [`docs/tui.md:114`](tui.md#L114)“终端停止消费或连接关闭时返回错误并取消所属运行”的表述不一致。

**半帧与旧缓冲问题**

`WouldBlock` 可以发生在 Ratatui 已写出部分 diff 之后。当前重试没有调用 `Terminal::clear`，没有强制 full redraw，也没有重新建立后端 cursor/escape 状态：

- Ratatui 自身文档明确说明，`try_draw` 出错后不承诺终端、光标和内部 buffer 仍同步。
- 下一次 `view::draw` 使用新的应用状态重新计算 diff，不能证明此前部分 ANSI/OSC 序列已经完整，也不能证明旧帧残留会被覆盖。
- `write_restore` 在恢复阶段写入 `ESC \\` 以结束可能的 OSC，但正常重试路径没有等价同步措施。

因此可能产生重复单元格、旧帧混合和控制序列残片。当前代码证明不了“重试一定恢复一致帧”；本轮也没有把该显示风险夸大为已确认的任意控制序列执行。

**现有测试为什么未覆盖**

[`crates/saya-tui/tests/terminal.rs:709-789`](../crates/saya-tui/tests/terminal.rs#L709-789) 只验证单次 `TerminalGuard::draw` 在慢速滴流下遵守帧预算、恢复 raw mode 和 FD flags，没有驱动外层 `run_loop`，也没有断言持续背压会退出，或部分写入后重试的字节流完整。

**建议**

- 在控制层增加持续背压总截止或连续失败上限，超时后按终端断开处理，取消所属运行并进入统一清理。
- 对可恢复的瞬时背压，在重试前执行明确的 full redraw/clear 和 cursor 状态重建；不要把部分 `try_draw` 当作未发生的写操作。
- 增加 PTY 测试：对端持续不读，驱动完整 `run_loop`，断言在总截止内取消运行、等待后台/插件收尾并恢复终端。
- 增加部分 CSI/OSC 写入后恢复的测试：在第 N 个字节注入 `WouldBlock`，恢复读取后验证没有旧控制残片、重复帧或过时审批帧。

### R-02 低（测试证据缺口）：`NSpid` 验收能证明记录到的插件主进程退出，不能证明全部后代已清理

**位置**

- [`crates/saya-core/tests/plugin_services.rs:45-61`](../crates/saya-core/tests/plugin_services.rs#L45-61)：MCP shell fixture。
- [`crates/saya-core/tests/plugin_services.rs:72-104`](../crates/saya-core/tests/plugin_services.rs#L72-104)：`NSpid` 到宿主 PID 的映射。
- [`crates/saya-core/tests/plugin_services.rs:491-499`](../crates/saya-core/tests/plugin_services.rs#L491-499)：对记录 PID 的 `kill(pid, 0) == ESRCH` 断言。

**已证明的内容**

本机实际运行 ignored 原生套件时，8 项全部通过，包含 `native_run_calls_plugin_mcp_and_hooks_and_releases_all_views`。该测试不是仅找到某个宿主 PID 就宣布成功：它先通过 `/proc/*/status` 的嵌套 `NSpid` 记录映射插件 PID，再于运行结束后对这些 PID 断言 `ESRCH`，同时核对 ViewPool、插件租约和恢复记录。

**未证明的内容**

- fixture 没有创建长期存活、调用 `setsid` 或脱离原进程组的后代；PID 断言只覆盖记录到的服务主进程。
- Hook 进程没有同等的 PID 消失断言。
- PID 映射测试没有覆盖 PID 重用、映射对象退出后的误归属、namespace 内多层级嵌套，以及宿主扫描时的进程启动身份（start time/exe）校验。
- macOS 后端文档明确将后代清理列为 `best_effort`；本测试通过不能被扩展解释为“脱离进程组的后代也一定被回收”。

因此它是主进程和内部租约的有效验收，不是完整后代树清理证明。这里记录的是测试缺口，不是声称当前实现已发生进程泄漏。

**建议**

增加平台适配的长期后代 fixture：主进程派生一个脱离进程组的后代，结束 Run 后分别检查主进程、后代、Hook 后代及代理桥接进程。记录 `/proc` start time 或等价平台身份，避免把 PID 重用当成清理成功；对 macOS 应明确区分“同组已清理”和“脱离组无法确认”，后者应保留 Unknown 而不是 Cleaned。

### 3.2 文件路径、私有根与原生执行

- 文件授权先 canonicalize 既有目标或新目标的既有父目录；worker 使用 `approved_target`、宿主保护快照和 `BoundGate` 再次绑定。参见 [`execution/worker.rs:174-205`](../crates/saya-core/src/execution/worker.rs#L174-205)。
- 私有保护快照包含路径、文件/目录 identity 和有限 hardlink 证据；扫描不完整时 hardlink 失败关闭。参见 [`tools/read/protection.rs:295-393`](../crates/saya-core/src/tools/read/protection.rs#L295-393)。
- 写入在持有父目录 capability 的情况下复核 expected version，并通过同目录临时文件 + rename 或排他 hard link 发布；创建和替换前再次检查取消与保护路径。参见 [`tools/write.rs:239-299`](../crates/saya-core/src/tools/write.rs#L239-299)。
- Linux 将保护遮罩放在读写 bind 之后，并覆盖系统目录别名；writable root 下缺失的保护路径返回 `unsupported_fs_policy`，不是静默放行。参见 [`execution/linux.rs:155-219`](../crates/saya-core/src/execution/linux.rs#L155-219)。
- macOS Seatbelt 使用参数化路径而非拼接不受控 SBPL 文本，保护 deny 最后发出以覆盖未来创建目标。参见 [`execution/seatbelt.rs:93-109`](../crates/saya-core/src/execution/seatbelt.rs#L93-109)。
- 启动环境经 unlink 的私有 FD 传递；payload exec 前设置未声明 FD 的 close-on-exec。参见 [`execution/transport.rs:122-167`](../crates/saya-core/src/execution/transport.rs#L122-167)、[`execution/fds.rs:28-100`](../crates/saya-core/src/execution/fds.rs#L28-100)。

本轮特别复核的 [`saya-app/src/lib.rs`](../crates/saya-app/src/lib.rs) 与 [`saya-app/src/extensions.rs`](../crates/saya-app/src/extensions.rs) 没有漏掉 Hook、Output、Memory 或 Checkpoint：

- 启动时已存在的 config/data/state/cache 与 `.saya/local` 加入原生保护；
- OutputStore、CheckpointStore、活动凭据目录随后强制加入；
- Memory 的 `MEMORY.md`、`memory/` 与锁文件加入；
- 插件 store、Hook journal、ViewPool 和 broker root 在插件初始化时同时加入逻辑文件保护和原生保护；
- `with_private_paths` 还保护未来路径，因此通用文件工具在 bypass 下也不能把这些根当成普通工作区文件。

### 3.3 网络代理、DNS 与重定向

- 每个上游连接都重新解析目标，检查全部地址并直接连接已检查的 IP，避免 hostname 二次解析形成典型 DNS TOCTOU。见 [`network.rs:272-296`](../crates/saya-core/src/network.rs#L272-296)。
- 混合 public/private 地址整组拒绝；IPv4 映射、6to4、Teredo、文档地址和常见 metadata/link-local 地址被排除。localhost 开发例外要求精确 origin 且只允许 loopback。
- HTTP absolute-form 与 Host 必须一致，CONNECT 必须显式端口，重复 Content-Length、chunked、upgrade、proxy 认证头均被拒绝或移除。见 [`network/http.rs:164-270`](../crates/saya-core/src/network/http.rs#L164-270)。
- broker 不主动跟随 redirect；客户端以后产生的新代理请求仍要重新通过 origin/address 检查。
- Linux 使用私有 network namespace + socat 到私有 Unix socket；macOS 只放行当前 broker 的 localhost TCP 端口。代理 listener 与 Unix socket 的生命周期在 payload/bridge 清理后结束。

本轮未确认直接外联、Unix socket、DNS rebinding、重定向或代理解析差异导致的可用绕过。

### 3.4 凭据与脱敏

- 原始 ToolCall 仅保留给授权和执行；RuntimeStore 在进入持久化前统一执行 `secrets::changes`，后续模型请求另有 `model_request` 检查。参见 [`runtime_secrets.rs:95-183`](../crates/saya-core/src/runtime_secrets.rs#L95-183)、[`runtime_secrets.rs:195-211`](../crates/saya-core/src/runtime_secrets.rs#L195-211)。
- `ProviderItem`、call ID 等不能安全改写的字段遇到秘密会失败关闭，而不是破坏签名/关联；普通正文和工具结果使用递归脱敏。
- 脱敏覆盖原始字符串、JSON 转义、Unicode escape、嵌套 JSON、重复键碰撞、深度/扫描上限和数字表示保真。无法确认安全时返回 `sensitive_data` 而不是输出原文。见 [`redaction.rs:271-369`](../crates/saya-core/src/redaction.rs#L271-369)。
- 独立模型审核若发现敏感参数会转人工，而不是把脱敏后语义不完整的操作交给模型放行。见 [`review.rs:266-285`](../crates/saya-core/src/review.rs#L266-285)。
- OAuth 每次 HTTP 操作前重新解析引用；刷新有跨进程刷新锁，撤销同时取得刷新锁与记录锁，撤销后的旧刷新不能写回。见 [`credentials/file.rs:261-287`](../crates/saya-core/src/credentials/file.rs#L261-287)、[`credentials/file.rs:563-605`](../crates/saya-core/src/credentials/file.rs#L563-605)。
- HTTP MCP 禁止自动重定向和重试，401 不重新发送原 MCP 请求；endpoint、issuer、canonical resource 和 scope 分别校验。
- 日志、事件、导出、TUI 与 OutputStore 均在各自边界再次脱敏；OutputStore 对新凭据会重新计算展示视图，保留原 digest 但扣留无法安全展示的 segment。

### 3.5 取消、后台与恢复

- 后台 worker 完成后才更新 JobStatus；shutdown 等待所有 Running 状态结束，再执行插件/服务清理，最后保存 RunFinished。见 [`background.rs:469-534`](../crates/saya-core/src/background.rs#L469-534)、[`runtime.rs:1901-2027`](../crates/saya-core/src/runtime.rs#L1901-2027)。
- MCP 启动 intent 在 spawn 前提交，启动后握手未确认会保留 unknown；pending/local 进程在 shutdown 中终止并等待。
- Hook 在 cleanup 确认前不会把结果视为成功，日志保存失败不会重放 intent；进程 registry 在 wait future 被 abort 后仍保留所有权。见 [`hooks/engine.rs:255-381`](../crates/saya-core/src/hooks/engine.rs#L255-381)、[`runtime_plugins/hooks.rs:455-559`](../crates/saya-core/src/runtime_plugins/hooks.rs#L455-559)。
- SQLite 恢复在单个事务中闭合悬空历史、将 running 转为 unknown、补终止结果并结束 interrupted run；重复恢复没有新的副作用。见 [`sqlite.rs:885-1160`](../crates/saya-core/src/sqlite.rs#L885-1160)。
- Checkpoint restore 对每个文件保存 applying/outcome，Unknown/Prepared/Applying 不允许直接重放；恢复只观察当前版本，不把 desired bytes 当成已由本进程写入的证明。

## 4. P1 Context、插件与协议核查

### 4.1 ContextBuilder、Compact 与遗忘

- wire counter 使用与最终 provider 相同的序列化路径，最终发送前再次 fit output；输出数字变化会重新计数。参见 [`provider/mod.rs:70-103`](../crates/saya-core/src/provider/mod.rs#L70-103)。
- `group_history` 要求 call/result 配对、ProviderItem 与语义镜像一致，未闭合组不会成为 compact 切点；最新用户原文在需要时独立逐字 replay。参见 [`context_builder/groups.rs:96-235`](../crates/saya-core/src/context_builder/groups.rs#L96-235)。
- Compaction 校验来源范围/hash、必留事实、引用和当前 ContextVersion，提交前再次核对完整历史水位；SQLite CAS 将 record 与 view 同事务发布。
- 遗忘版本参与 ContextView 兼容性，失效组替换只保留机械观察；OutputStore 查询与后台结果再次应用 RetiredOutputAcl，旧输出不能借 output_ref 或后台状态重新进入模型。

### 4.2 插件与 Hooks

- 包内容按实际 UTF-8 路径字节计算 tree digest，Unicode NFC + casefold 仅用于碰撞检测；安装消费封存字节而不是重读可变源目录。
- lock 校验依赖版本/digest、闭包、alias 和来源；enable/acquire 时重新验证内容与宿主 feature，更新后的新 digest 需要新的显式 enable。
- workspace enablement 绑定真实设备/inode；停止或撤回的租约保持 Unknown/pin，只有实际清理证据齐全后才释放。
- 插件 process 使用独立 read/write roots、私有包 view、显式环境引用和原生隔离；HTTP origin 是包声明、启用 grant 和宿主 broker 的交集。
- Hook check 的 pass/abstain 不授予父操作权限；父操作仍走普通审批。Hook 超时/格式错误/check deny 阻止父派发，observer 失败保留诊断。
- 本轮实际原生测试通过 8 项，覆盖 PLAN 不启动、Manual 审批数、check veto、禁用后禁止调用、准备中止清理和真实主进程退出；R-02 所列后代边界仍未覆盖。

### 4.3 三协议适配

- Chat 按 tool index 聚合参数，要求连续 index、唯一 call ID、合法 JSON object 和匹配 finish reason；不完整流不会派发。
- Responses 交叉检查 text/argument delta、done item、item ID 和最终 output；function result 通过 call_id 配对，opaque reasoning 与语义项相邻回放。
- Anthropic 保留 thinking/signature/redacted 原生块，tool_use 的 partial JSON 只有完整 object 才能形成调用，多个 tool_result 紧随调用并逐一关联。
- 三协议均不自动拼接部分响应重试；`store: false`（Chat/Responses）、禁止 redirect/retry、错误信息不携带响应正文或鉴权值。
- ContextBuilder 在恢复后再次验证协议原子组和 ProviderItem 镜像，避免把另一轮或另一协议的调用结果配错。

## 5. P2 持久化、CLI 与本轮四处重点

### 5.1 数据库迁移、WAL 与导出发布

- schema v1 迁移先用在线 backup 生成独立文件，校验后同步，再事务更新版本；更高版本或损坏数据库拒绝打开。
- WAL 只读快照检查 salt、滚动 checksum 和最后提交点，遇到无效尾部停止在已验证前缀，不创建源侧 SHM/附加文件。
- 导出采用固定父目录 capability、0700 staging、0600 内容文件、文件 sync、排他 hard link、目录 sync、最终 identity 和 SHA-256 复核。发布后核对失败返回 `export_publish_uncertain`，不会覆盖已有目标。
- PLAN 导出同时拒绝当前与保存工作区内路径，防止借导出恢复写权限。

### 5.2 `WouldBlock` 重点复核

确认存在 R-01。单次写入和单帧有界并不等于整体背压有界；控制层重试语义是当前缺陷点。

### 5.3 `NSpid` 重点复核

主进程清理断言有效且本机通过，但不能替代脱离进程组后代、Hook 后代与 PID 重用场景，见 R-02。

### 5.4 CLI HOME 与工作区分离

当前夹具将 HOME、workspace 和 XDG 根分离是合法隔离：可以避免测试读写真实用户目录，并允许显式构造“某一存储根在 workspace 内”的反例。已有测试 [`cli.rs:331-430`](../crates/saya-cli/tests/cli.rs#L331-430) 验证 PLAN 在 data/state/cache 任一重叠时拒绝且不创建 SQLite side files。

`HOME == workspace` 且未设置 XDG 时，默认 data/state/cache 会落在 HOME 下，因此 `session::check_roots` 应在 PLAN 启动时拒绝，而不是被测试夹具静默放行。当前实现确实执行该校验，但缺少一个不设置 XDG、直接让 HOME 与 workspace 相同的专门回归。建议补充以下边界：

1. `HOME == workspace` 且 XDG 全未设置，PLAN 在创建任何文件前失败；
2. 同一条件但 XDG 全部指向 workspace 外，允许运行，并验证全局 Memory、Hook、Output、Checkpoint 根仍被保护；
3. HOME 与工作区互为符号链接别名、私有根尚不存在时，仍按 canonical identity 判断；
4. config 文件自身位于 workspace 内时，原生执行和文件 worker 均不能读取/修改它。

这是覆盖补强建议，不是当前已确认越权。
