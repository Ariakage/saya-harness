## 2. 复审发现

### F-01 低（测试证据缺口）：原生后代验收仍使用聚合采样，并完全错过最后一次模型调用之后的 `run.finished` Hook 后代

**位置**

- [`plugin_services.rs:211-229`](../crates/saya-core/tests/plugin_services.rs#L211-L229)：唯一的进程与 survival marker 采样位于 `FixtureModel::start`。
- [`plugin_services.rs:369-375`](../crates/saya-core/tests/plugin_services.rs#L369-L375)：同一 fixture 同时注册 `run.started` 和 `run.finished` 两个 observer Hook。
- [`plugin_services.rs:573-584`](../crates/saya-core/tests/plugin_services.rs#L573-L584)：最终只要求聚合集合 `observed.len() >= 2`，并读取此前模型调用设置的布尔值。
- [`runtime.rs:1877-1907`](../crates/saya-core/src/runtime.rs#L1877-L1907)：`run_inner` 及其模型循环先返回，随后才执行 `run.finished` Hook 和服务清理。

**已经补强的部分**

1. 服务 fixture 在 Linux 使用 `setsid` 构造脱离进程组的后代，在 macOS 构造当前后端能够处理的同组后代。
2. `ProcessIdentity` 同时记录 PID 和启动时间；Linux 读取 `/proc/<pid>/stat`，macOS 使用 `proc_pidinfo`。
3. 清理后同时检查启动身份已变化或消失、`kill(pid, 0)` 失败且错误为 `ESRCH`，不会仅凭一个仍然可复用的 PID 宣布成功。
4. Hook 子进程增加延迟 survival marker，尝试覆盖“进程仍存活并继续产生副作用”的情况。
5. 本机真实原生插件验收 8/8 通过，说明这些新增路径至少在当前 macOS 环境中没有破坏既有功能。

**缺口一：聚合数量不能证明每类对象均被覆盖**

采样循环依次寻找 `pid`、`server-child`、`hook-child`，但把三类对象放进同一个 `Vec<ProcessIdentity>`，最终只断言总数至少为二。测试没有分别断言：

- 服务主进程已被记录；
- 服务后代已被记录；
- `run.started` Hook 后代已被记录；
- `run.finished` Hook 后代已被记录。

因此，若服务后代根本没有成功创建、来不及被采样或 PID 映射失败，只要服务主进程和某个 Hook 后代被记录，总数条件仍可通过。反过来，只记录服务主进程和服务后代也可能满足该条件。测试名称和整改说明表达的是分角色覆盖，断言实际证明的是聚合覆盖。

**缺口二：`run.finished` 后代位于所有采样点之后**

`FixtureModel::start` 是读取 PID 文件和 `hook-child-survived` 的唯一位置。正常远程调用完成后，最后一次模型调用返回最终文本并离开 `run_inner`；此后才运行 `run.finished` Hook。因此：

- 最后一次 Hook 创建的新后代不可能被后续模型调用记录；
- 最后一次 Hook 的 survival marker 即使随后写出，也不会再被读取；
- 测试结束时的 `assert!(!*model.escaped_hook_child...)` 只是读取旧布尔值，不是重新观察文件系统或进程状态；
- Hook journal 的 `CleanupState::Cleaned` 是生产实现自身给出的状态，不能替代对最后一项 Hook 后代的独立宿主侧检查。

所以，即使把聚合数量提高为三个，也仍不能证明 `run.finished` 的后代清理。需要一个在该 Hook 执行期间进行宿主侧采样、并在清理后复核精确身份的同步设计，而不是只增加模型调用次数或总数阈值。

**影响与定级**

这是验收证据缺口，不是已确认的生产进程泄漏。其风险在于未来若服务后代创建失败、特定 Hook 的清理回归或某事件分支漏杀后代，当前测试仍可能通过，而文档会把证据说得比实际更强。因此定为低等级，但 R-02 不应标记为完全关闭。

**建议**

1. 按 `server-main`、`server-child`、`hook-started-child`、`hook-finished-child` 分键记录，不允许聚合计数互相替代。
2. 为每个必需对象设置明确的“已创建、已映射、已取得启动身份”前置断言；任一项缺失都应使验收失败。
3. 让 `run.finished` fixture 在宿主完成采样前保持可控同步，再允许其退出；运行结束后对该精确 PID＋启动身份复查。
4. survival marker 只能在对应观察窗口和文件根仍有效时作为辅助证据，不能把“文件不存在”单独解释为“进程不存在”。
5. 在 Linux 实际运行脱离组分支；macOS 主动脱离进程组的后代继续保留 `best_effort`／Unknown 边界，不以同组测试替代。

### F-02 低（测试隔离）：无限后代 fixture 没有失败路径回收，测试回归时可能遗留 CI 进程

**位置**

- [`plugin_services.rs:50-54`](../crates/saya-core/tests/plugin_services.rs#L50-L54) 与 [`plugin_services.rs:70-76`](../crates/saya-core/tests/plugin_services.rs#L70-L76)：服务和 Hook 后代均执行无限 `while :; do sleep 1; done`。
- [`plugin_services.rs:573-585`](../crates/saya-core/tests/plugin_services.rs#L573-L585)：唯一的进程身份断言位于 `runtime.run` 成功返回之后。

测试没有为已观察 PID 注册 `Drop`、scope guard 或其他失败路径回收器。若生产清理发生回归、fixture 中途 panic，或某个前置断言在最终检查前失败，Rust 测试会展开并删除 `TempDir`，但删除临时目录不会终止进程。Linux 的脱离组后代尤其不受测试进程退出约束，孤立的 shell 还会持续启动 `sleep`。

这不是当前 8/8 通过时遗留进程的观察结果，而是“测试本来用于捕获泄漏时，自身可能放大泄漏”的确定性隔离缺口。建议只在测试作用域内保存并校验每个进程身份，并在所有退出路径执行 bounded best-effort kill／wait；不能把兜底清理放到最终断言之前，否则会把真实回归掩盖为通过。

### F-03 低（测试时序）：resync 探针三个阶段共享一个五秒期限，可能产生负载相关假失败

[`terminal.rs:493-525`](../crates/saya-tui/tests/terminal.rs#L493-L525) 在开始等待前只创建一个 `deadline`，随后依次用于：

1. 等待父进程创建 `start`；
2. 最多 2048 次真实 PTY 绘制并填满输出队列；
3. 报告 `stalled` 后等待父进程创建 `resume`。

中间绘制每帧本身可有 250ms I/O 预算。高负载或调度延迟下，即使父进程在收到 `stalled` 后立即写入 `resume`，子进程也可能在进入 resume 等待时已经越过最初五秒期限，返回 `TimedOut`。这不表示生产重同步错误，但会降低新增验收的可靠性。

建议在报告 `stalled` 后为 resume 等待重新建立独立期限，或复用每次新建期限的文件等待 helper。F-03 不改变 R-01 已修复的判断，因为本轮真实 PTY 测试和完整 slow-consumer 旅程均通过；它记录的是尚未动态复现的负载脆弱性。

## 3. R-01 修复核实

### 3.1 持续背压现在有总截止

[`controller.rs:883-893`](../crates/saya-tui/src/controller.rs#L883-L893) 定义两秒 `DRAW_BACKPRESSURE_WAIT` 并保存首次失败时间；[`controller.rs:1001-1042`](../crates/saya-tui/src/controller.rs#L1001-L1042) 的行为为：

- 成功绘制后清零背压起点并清除 dirty；
- `WouldBlock` 保留 dirty，并从首次失败累计，而不是每帧重新获得两秒；
- 到期且存在活跃运行或 UI 任务时，设置退出码 1 并调用统一的 `app.cancel()`；
- 空闲时直接返回输出错误；
- 运行结束后仅在活跃运行与 UI 任务均清理完成时退出。

[`controller.rs:492-528`](../crates/saya-tui/src/controller.rs#L492-L528) 的取消会使排队 Compact、延迟模式、待审批和所属运行失效；[`controller.rs:873-881`](../crates/saya-tui/src/controller.rs#L873-L881) 在 `run_loop` 后仍执行 `app.shutdown`，等待活跃任务、后台与 UI 工作收尾。原问题中“对端永不读取便无限维持运行”的机制已被切断。

### 3.2 失败帧后不再复用不确定 Ratatui 状态

[`terminal.rs:24`](../crates/saya-tui/src/terminal.rs#L24) 的恢复序列包含 CAN、ST、SGR reset、清屏、光标归位和隐藏光标。[`terminal.rs:439-472`](../crates/saya-tui/src/terminal.rs#L439-L472) 在下一次绘制时：

1. 用同一私有输出对象重新创建 `Terminal`，得到两份空缓冲和新的 cursor 状态；
2. 先执行用户渲染闭包，再开启帧 I/O 预算；
3. 在 Ratatui flush diff 之前写入恢复序列；
4. 从空缓冲生成完整帧，而不是把失败帧当作未发生；
5. 每次失败继续保留 `resync = true`，直到一次完整绘制成功。

锁定的 `ratatui-core 0.1.2` 实现中，`try_draw` 先 flush diff，再处理 cursor、交换 buffer 和 flush 后端；任一步失败都不能假设此前输出完整。本次重建 `Terminal` 加物理清屏与该错误语义相符。

### 3.3 测试与实际旅程证据

- [`terminal.rs:766-831`](../crates/saya-tui/tests/terminal.rs#L766-L831) 的 PTY 测试先使真实输出队列产生 `WouldBlock`，恢复读取后检查重同步序列、新帧正文、旧 A/B 单元格不重放，以及 raw mode、termios 和 FD flags 恢复。
- [`tui_journey.py:2609-2675`](../scripts/release/tui_journey.py#L2609-L2675) 驱动完整控制环：先启动真实后台 shell／`sleep`，再停止消费 PTY；断言程序无需外部信号即以退出码 1 结束、两个后台 PID 均消失、终端属性和 FD flags 恢复。
- 本轮实际执行固定 release 程序的完整 `just smoke`，其中该 slow-consumer 旅程和其余 25 条 TUI 旅程全部通过。

据此，R-01 的总截止、取消清理和旧缓冲重绘均得到源码与动态证据支持。更精细的“第 N 个字节刚好切断某一种 CSI/OSC”仍可成为后续故障注入矩阵，但不构成当前已确认缺陷。

## 5. HOME／XDG／config 回归核实

### 5.1 PLAN 在 HOME 与工作区重叠时先于存储创建失败

[`cli.rs:434-462`](../crates/saya-cli/tests/cli.rs#L434-L462) 分别使用 HOME 直接等于 workspace、HOME 为 workspace 的符号链接别名，且不设置 XDG。两种情况下都断言退出码 2、出现 PLAN storage overlap 错误，并比较运行前后的工作区目录项集合。

实现链 [`session.rs:28-60`](../crates/saya-app/src/session.rs#L28-L60) 会解析现存祖先的 canonical 路径并补齐未来组件，同时检查双向包含关系。该逻辑与新增测试一致，能够覆盖未来存储根和符号链接别名，不需要先创建 SQLite 文件。

### 5.2 XDG 外置时允许运行，现有 Memory 仍不能由普通文件工具读取

[`cli.rs:465-530`](../crates/saya-cli/tests/cli.rs#L465-L530) 创建真实的 workspace／HOME 同根场景，将 data/state/cache 全部指向外部临时目录，预先创建 `.saya/MEMORY.md`、memory 目录和锁文件，再让模型调用 `read_file`。测试验证 CLI 正常完成、协议交互进入第二轮且该工具结果不成功。

[`lib.rs:330-355`](../crates/saya-app/src/lib.rs#L330-L355) 将默认 `HOME/.saya` 下的 Memory 正文、目录和锁同时加入原生保护与运行时私有路径；XDG 外置不会把这组根从保护集合移除。

该测试可以使用更具体的错误码和唯一正文 sentinel 加强诊断，但“保护被完全移除后读取成功”仍会使当前断言失败，因此不另列为缺陷。

### 5.3 工作区内 config 对文件和进程工具均受保护

[`cli.rs:3380-3437`](../crates/saya-cli/tests/cli.rs#L3380-L3437) 在 config 内加入唯一 sentinel，依次驱动 `read_file` 和 shell 覆盖，再验证：

该用例同时覆盖逻辑文件边界与原生命令边界。本轮没有发现新增 HOME／XDG 测试通过共享环境、真实 HOME 或错误工作目录造成的假阳性。
